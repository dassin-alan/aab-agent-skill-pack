# Agent Efficiency

## 核心原则

Agent 最大的效率杀手：**在没有新信息的情况下重复做同样的事**。

"让我探索一下" 通常是浪费。直接执行，错了再改。

## 三大效率法则

### 法则 1：默认直接执行

```
用户说"改 A" →
  ❌ 读 A 文件 → 读 B 文件（可能有关系？）→ 读 C 文件（也许用得上？）→ 改 A
  ✅ 读 A 文件 → 改 A → 完成

用户说"加个功能" →
  ❌ 探索项目结构 → 找类似实现 → 看 3 个参考 → 写代码
  ✅ 找 1 个类似实现（如果有）→ 写代码 → 跑一下 → 根据结果调整
```

### 法则 2：一次搜索，记住结论

```
❌ 第 1 轮：Grep "Button" → 找到 3 个文件
   第 5 轮：又 Grep "Button" → 同样的结果
   第 10 轮：再搜一次确认

✅ 第 1 轮：Grep "Button" → 记住有 3 个文件
   第 5 轮：直接用记忆中的结果
   除非代码被改过了，否则不重复搜索
```

### 法则 3：信任你的判断

```
❌ "这应该是 React 项目...让我确认一下" → 读 package.json → 看配置 → 确认是 React
✅ "应该是 React 项目" → 直接按 React 写 → 如果报错再调整

❌ "这个函数应该接受 string...让我确认一下" → 读类型定义 → 读调用处 → 确认
✅ 写 string → 类型检查会告诉你对不对
```

## 何时探索、何时执行

| 场景 | 策略 |
|------|------|
| 熟悉项目，简单改动 | 零探索，直接改 |
| 熟悉项目，中等改动 | 读 1 个相关文件，然后改 |
| 新项目，简单需求 | 读 1 个文件了解风格，然后写 |
| 新项目，复杂需求 | 允许 2-3 个文件探索，不要更多 |
| 安全关键代码 | 多读多确认（破例允许） |
| Bug 难以复现 | 允许扩大搜索 |

## 快速判断项目类型

不用探索，从文件名就能判断：

```
package.json + src/App.tsx         → React + TypeScript
package.json + src/App.vue         → Vue
requirements.txt / pyproject.toml   → Python
Cargo.toml                         → Rust
go.mod                             → Go
index.html（单文件）                → 纯 HTML
```

看一眼就知道，不用 `ls` 整个目录。

## 避免确认性搜索

确认性搜索 = 你已经知道答案，只是想"确认一下"。

```
确认性搜索的例子：
- "让我确认一下这个文件还在不在"（你知道它在）
- "让我确认一下这个函数签名"（你刚才见过）
- "让我确认一下没有其他地方引用"（改动很简单，不可能影响其他地方）

不要做的原因：
- 工具返回结果不会比你记忆中的更新
- 如果真的错了，测试/运行会告诉你
- 花 token 确认已知信息 = 纯浪费
```

唯一的例外：安全相关代码（密码、权限、SQL 注入风险）。

## 迭代优于预读

```
预读策略（慢）：
  读 5 个相关文件 → 理解全部 → 开始写 → 发现一个没理解 → 再读 2 个 → 写完
  消耗：7 个文件读取，大部分可能没用上

迭代策略（快）：
  写第一版 → 跑 → 报错指向 A 文件 → 读 A → 改 → 跑 → 过
  消耗：1 个文件读取（A），而且只是在报错后才读
```

## Stop Conditions（停止条件）

以下情况立即停止探索，直接执行：

```
1. 找到目标文件 → 停，开始改
2. 找到目标函数/组件 → 停，直接用
3. 找到一条可靠的实现路径 → 停，开始写
4. 用户的需求可以完成，不需要更多上下文 → 停
5. 你已经在重复搜索同一个关键词 → 停，用记忆中已有的结果
```

**不要为了"穷举所有可能"继续搜索。** 找到一个就够了。如果用户需要"所有"，他们会明确说。

## 和 aab-low-token 的关系

- `aab-low-token` 控制**每次操作**的 token 消耗
- 本 Skill 控制**操作次数**——减少不必要的操作

两个 Skill 互补：
- Low Token 说"每次搜索要精确"
- Agent Efficiency 说"不要搜索你已经知道的事"
