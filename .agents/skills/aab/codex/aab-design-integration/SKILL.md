# Design.md Integration

## 核心概念

Design.md 是项目设计文档的可执行版本。它不是给人看的，是给 Agent 看的。

```
传统方式：设计稿(Figma) → 人看 → 人写代码
本方式：设计稿(Figma) → Design.md → Agent 直接写代码
```

## Design.md 格式

AAB 的标准 Design.md 模板：

```markdown
# [项目名] Design.md

## 视觉规范
- 配色：[引用 aab-frontend-ui 或自定义色板]
- 字体：[系统字体 / 指定字体]
- 间距：[8px 系统 / 自定义]
- 圆角：[具体数值]
- 阴影：[具体数值]

## 页面结构
1. [页面名]：[用途 + 关键元素]
2. [页面名]：[用途 + 关键元素]

## 组件列表
- [组件名]：[样式 + 状态 + 数据来源]

## 数据流
- [数据名]：[来源 → 展示位置 → 更新频率]

## 特殊约束
- [例如：必须离线可用]
- [例如：投影仪兼容]
```

## 什么时候需要 Design.md

```
需要：比赛 Demo（3+ 页面）
需要：长期维护的项目
需要：有明确 UI 设计稿的项目
不需要：单文件 HTML 原型（口头描述够用）
不需要：临时工具页面
```

## Design.md → 代码

当 Agent 拿到 Design.md 后：

```
1. 先读取 Design.md（一次性加载全部视觉规范）
2. 按页面结构顺序开发
3. 每个组件对照组件列表实现
4. 完成后对照 Design.md 自查
```

这样就不需要在每次对话中重复描述视觉要求。

## 与 Figma/设计稿的关系

```
有 Figma：
  Design.md 从 Figma 提取关键数据（颜色值、间距、字体）
  不需要描述布局（Agent 看 Figma 截图 + Design.md 数据）

没有 Figma：
  Design.md 就是设计稿
  需要更详细的页面结构和组件描述
  引用 aab-frontend-ui 的默认配色
```

## 维护

```
开始开发时创建 Design.md
每次修改视觉规范时更新 Design.md
项目结束时 Design.md 归档（作为交付物的一部分）

不要过度维护：
  - 小的样式调整不需要更新 Design.md
  - 只记录"约束"，不记录"实现"
```

## 示例：一个比赛 Demo 的 Design.md

```markdown
# 智农 Dashboard Design.md

## 视觉规范
- 配色：暗色科技风（aab-frontend-ui 默认色板）
- 强调色：accent-cyan（#00d4cc，农业/数据感）
- 字体：系统字体栈
- 圆角：8px（卡片）、6px（按钮）
- 间距：16px 基准网格

## 页面结构
1. 首页 Hero：项目名 + 一句话 + 数据预览（3 指标）
2. 数据看板：地图 + 趋势图 + 风险列表
3. 关于：技术路线 + 团队介绍
4. 演示结束页：联系信息 + 二维码

## 组件列表
- 指标卡片：数值 + 标签 + 对比箭头，hover 发光
- 趋势图：Canvas 手写折线图，2 条线（预测 vs 实际）
- 风险列表：表格，按风险等级着色
- Hero CTA：渐变按钮，跳转看板

## 数据流
- 监测数据：硬编码 JS 对象 → 指标卡片 + 趋势图
- 风险数据：硬编码 JS 数组 → 风险列表

## 特殊约束
- 单文件 HTML，零外部依赖
- 离线可用，所有数据内置
- 投影仪兼容（高对比度模式可选）
```
