# Competition Demo

## 六步项目执行法
这是 AAB 已验证的比赛项目开发方法论。按顺序执行，不要跳步。
### 第一步：确定终局

明确"这个项目最终用来干什么？"
| 场景 | 特点 | 关键要求 |
|------|------|----------|
| 比赛答辩 | 评委 5-10 分钟，看项目书/PPT+Demo | 可信、有数据、能回答问题 |
| 老师展示 | 老师更关心 做得怎么样 而非 能不能赚钱 | 技术路线清晰、有完成度 |
| 课堂汇报 | 同学互评，时间短 | 视觉好、Demo 能跑、不要翻车 |
| 自媒体传播 | 需要抓眼球 | 酷炫、有传播点、短平快 |

**第一步就定下来，后面所有决策都围绕这个。**

### 第二步：计算胜率

逐项检查：

```
[ ] 痛点是否明确？（能用一句话说清楚）
[ ] 展示效果是否强？（评委/老师 5 秒内能看懂）
[ ] 技术路线能否解释？（不要说"AI 自动分析"，说具体怎么做的）
[ ] 数据来源是否可信？（公开数据 > 自采数据 > 模拟数据 > 没有数据）
[ ] 评委是否容易理解？（不用专业术语装逼）
[ ] 用户是否觉得有用？（如果自己是用户，会下载吗？）
```

如果超过 2 项打不了勾 → 先解决这些再写代码。
### 第三步：切换上帝视角

站在不同角色的角度审视项目：

```
老师视角：
  - 这个项目有技术含量吗？
  - 工作量够不够？
  - 学生真的理解自己在做什么吗？

评委视角：
  - 创新点在哪？（一句话）
  - 和现有方案比有什么优势？
  - 商业模式能跑通吗？
  - 团队能做得出来吗？

用户视角：
  - 我为什么用这个？
  - 比我现在用的好在哪里？
  - 免费吗？好用吗？安全吗？

竞品视角：
  - 他们有的我没有 → 这是差异点
  - 我有的他们没有 → 这是优势
  - "没有竞品" → 要么没调研，要么没市场
```

### 第四步：模块化搭建
#### 页面模块（Demo/产品）
```
必须有的：
  - Hero 区：项目名 + 一句话价值主张 + CTA
  - 功能区：核心功能展示（3-4 个）
  - 数据看板：关键指标可视化

加分项：
  - AI 推荐 / 智能分析模块
  - 案例展示 / 对比
  - 技术路线 / 架构图
  - 数据来源说明
  - 报告生成 / 导出
```

#### 文案模块（项目书/PPT）
```
项目名公式：
  [核心功能] + [目标用户] + [一句话差异化]
  例："智农——基于多源数据的农作物病虫害预警平台"

必须写的段落：
  - 痛点（300 字，要有具体数据和场景）
  - 方案（200 字，说清楚怎么做）
  - 创新点（3 个，每个 50 字）
  - 商业模式（200 字，谁付钱、为什么付、多少钱）
  - 应用场景（2-3 个具体场景）
  - 竞品分析（至少 3 个竞品，有对比表）
  - 风险对策（至少 2 个风险，有应对方案）

答辩话术：
  - 开场 30 秒：项目名 + 解决什么问题 + 为什么是你
  - 技术介绍 60 秒：核心路线 + 关键数据 + 创新点
  - 商业模式 30 秒：谁付钱 + 市场多大
  - 收尾 30 秒：团队优势 + 未来计划 + 呼吁
```

#### 技术模块
```
前端：HTML 单文件 / React（取决于复杂度）
  - 暗色科技风（参考 aab-frontend-ui）
  - 2-3 个核心页面，不要更多
  - 数据可视化用 Chart.js 或纯 Canvas

数据：
  - 数据来源要可追溯
  - 数据量要能支撑结论
  - 用"模拟数据"时标注清楚
AI（如果有）：
  - 不要写"基于深度学习"——写具体用了什么
  - 能解释为什么用这个算法
  - 有对比实验更好（但比赛 Demo 通常不需要）
```

### 第五步：认知包装

```
包装公式：普通功能 → 高级表达 → 可信证据

✗"系统可以查看数据"
✓"多维度数据可视化看板，支持实时监控与历史趋势对比"
   →   展示一张实际数据截图或 Demo 动图

✗"用了 AI 技术"
✓"基于 XGBoost 的多因子预测模型，在测试集上准确率达 92.3%"
   →   展示模型对比表格或预测效果图
```

**底线**：
- 不虚构接口
- 不夸大已实现的功能
- Demo 能跑的才算已实现
- 计划中的写"待开发"，但要有时间表
### 第六步：内存释放

每周检查一次（建议周五下午）：

```
[ ] 这个项目还值得继续投入吗？
[ ] 哪些工具/技术暂时不需要折腾了？
[ ] 哪些想法可以先放进备忘录？
[ ] 哪些事情只是让我焦虑但不提高胜率？
[ ] 下周最关键的三个动作是什么？
```

## Competition Scoring Lens（比赛评分导向）

每次修改 Demo 之前，确认这个改动至少提升以下一项：

```
[ ] 视觉冲击力 —— 评委 5 秒内能否记住这个画面？
[ ] 问题清晰度 —— 痛点是否一针见血？
[ ] 技术可信度 —— 技术路线是否有说服力？
[ ] 数据可信度 —— 数据来源是否可追溯？
[ ] 产品完整度 —— 看起来像一个能用的产品，不只原型？
[ ] 商业潜力 —— 商业模式是否成立？（比赛评委关心这个）
[ ] 展示安全性 —— 翻车概率降低了吗？
```

如果改动不影响以上任何一项 → 这个改动不是当前优先级，放后面。
## 比赛材料清单

### 必需

- [ ] 项目书（Word/PDF，含封面、目录、正文、参考文献）
- [ ] 答辩 PPT（10-15 页，15 分钟以内）
- [ ] Demo（可运行、可展示核心功能）
- [ ] 视频（1-2 分钟，展示核心价值，不做操作教程）
### 建议

- [ ] 1 页项目简介（给评委快速翻阅）
- [ ] 答辩预演（至少 3 遍，找人挑毛病）
- [ ] 备用方案（网络断了 / 设备不兼容 / Demo 崩了怎么应对）
## Demo 翻车预防

```
翻车点 1: Demo 依赖网络 → 做本地离线版
翻车点 2: 数据硬编码后忘了标注 → 所有模拟数据加注释
翻车点 3: 演示路径没测试 → 按"评委看到的第一个画面 → 核心功能 → 亮点 → 结束"走一遍
翻车点 4: 代码没备份 → 答辩前 git commit + U 盘备份
翻车点 5: 投影仪颜色失准 → 暗色主题在投影仪上可能看不清，准备一个高对比度版本
```

## 与 aab-frontend-ui 的关系
比赛 Demo 的前端默认使用 `aab-frontend-ui` 的暗色科技风。但有比赛特殊要求时以比赛要求为准（如学校模板、比赛固定格式）。
