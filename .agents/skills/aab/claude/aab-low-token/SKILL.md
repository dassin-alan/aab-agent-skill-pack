# Low Token

## 核心原则

每次工具调用都在烧 token。你的目标是：**用最少的上下文换最大的产出**。

不是"少做事"，而是"精确做事"。

## Hard Rules（硬性限制）

这些是硬性数字，不是建议。除非用户明确要求"全面检查"，否则必须遵守：

```
1. 默认不扫描整个仓库
2. 最多读 3 个文件后就动手改第一版
3. Read 长文件必须用 limit/offset，单次不超过 150 行
4. 命令输出默认加 | tail -50，除非需要完整日志
5. 不要为了"确认"重新读文件——工具返回值就是确认
6. 扩展上下文到当前模块之外前，先问
```

### 任务分级预算

| 级别 | 场景 | 最多文件读取 | 适用 |
|------|------|-------------|------|
| **Tiny** | 改文字/颜色/小样式 | 1 个文件 | 90% 的日常改动 |
| **Normal** | 加一个功能/组件 | 3 个文件 | 中等改动 |
| **Heavy** | 全项目重构/审计 | 不限（但先列计划） | 用户明确要求的 |

默认从 Tiny 开始。发现不够再升到 Normal。不要上来就 Heavy。

## 搜索策略：窄 → 宽，不是宽 → 窄

```
❌ 上来就 Glob **/*.ts → 200 个文件 → 再逐个 Grep
✅ 先用 Grep 精确匹配 → 找到文件 → 只 Read 相关行
```

### 优先级

| 优先级 | 工具 | 适用场景 |
|--------|------|----------|
| 1 | Grep（精确模式） | 知道函数名/类名/关键字 |
| 2 | Grep（glob 过滤） | 知道文件类型 + 关键字 |
| 3 | Glob（窄 pattern） | 知道目录 + 文件扩展名 |
| 4 | Glob（宽 pattern） | 不知道确切位置，需要扫描 |
| 5 | Agent（Explore） | 需要跨多个目录/多轮搜索 |

规则：**能用 1 不用 2，能用 2 不用 3。前 3 级都试过再考虑 Agent。**

## 读取策略：按需分页，不全量

```
❌ Read file_path（2000 行全读，只用前 50 行）
✅ Read file_path limit=80（只读需要的范围）
```

- 读之前先想：我需要这个文件的哪一部分？
- 已知函数名 → Grep 找行号 → Read offset + limit
- 只需要文件结构 → Grep `^function\|^class\|^export` 代替 Read
- 只需要 import → `head -20` 代替全文件

## 停止策略：找到就停

```
❌ Grep 找到了目标函数 → "让我再确认一下其他文件有没有"
✅ Grep 找到了 → 直接用 → 不再搜索
```

- 找到一个匹配 ≠ 可能还有更多 → 除非任务明确要求"全部"
- 一个文件能回答的问题，不读第二个
- 用户问"A 在哪" → 找到一个位置就回答，不穷举

## 并行策略：独立的就一起发

```
❌ Read file1 → 等结果 → Read file2 → 等结果 → Read file3
✅ 同时 Read file1, file2, file3（三个独立操作，一个回合）
```

- 两个操作之间没有依赖 → 同一批发出
- 不要"先读一个看看"——提前想好你可能需要什么，一起读

## 命令输出：强制过滤

```
❌ npm test（3000 行输出全进上下文）
✅ npm test 2>&1 | tail -30（只要最后 30 行）
```

- 构建/测试命令 → 默认只要最后 50 行和失败摘要
- 日志查看 → 用 grep 过滤，不 tail -f 全量
- Git diff → 先 `--stat`，再按需 `diff <specific-file>`
- 命令输出超 100 行 → 截断，加 `| head -100` 或 `| tail -50`

## 验证策略：信任工具返回值

```
❌ Edit 完 → Read 全文件确认
✅ Edit 返回 success → 直接继续（工具已验证）
```

- Edit/Write 返回成功 = 已写入，不需要重新 Read 确认
- Bash 返回 exit 0 = 成功，不需要再跑一遍确认
- 只在工具报错或行为异常时才验证

## 探索 vs 执行

```
❌ "让我先探索一下代码库结构"（5 个 Read + 3 个 Glob → 2000 token）
✅ 直接写代码 → 跑测试 → 根据报错定位（0 探索 token）
```

- 对代码库不熟悉 → 最小探索（1-2 个 Read）后直接尝试
- 报错会告诉你哪里不对 → 比预读 10 个文件更高效
- 熟悉的项目 → 零探索，直接做

## Token 预算意识

每轮对话在心里估一下：
- Read 全文件 ~500-2000 token
- Grep 输出 ~100-500 token
- Glob 列表 ~50-200 token
- Agent（Explore） ~1000-5000 token
- 命令输出（无过滤） ~500-5000 token

**你的目标**：单次任务总 token < 你产出的代码 token 的 3 倍。

## 何时破例

以下情况允许放宽限制：
- 安全相关代码 → 可以多读确保理解正确
- 用户明确说"全面检查""仔细过一遍" → 按用户要求
- 首次接触的新项目 → 允许 1 次中等探索（3-5 个 Read）
- Bug 难以复现 → 允许扩大搜索范围

## 反模式速查

| 反模式 | 问题 | 改正 |
|--------|------|------|
| "让我全面了解一下" | 无边界探索，token 黑洞 | 只了解当前任务需要的 |
| "再确认一下" | 不信任工具返回值 | 工具说成功就是成功 |
| "顺便看看" | 范围蔓延 | 只做用户要求的 |
| "我搜一下有没有类似的" | 找到答案后继续搜 | 找到就停 |
| Read 整个文件 | 只要 10 行却读了 500 行 | Grep 定位 + offset 读取 |
| 逐个 Read（串行） | 浪费回合数 | 独立读取并行发出 |
| 命令输出不过滤 | 3000 行日志进上下文 | 管道过滤，只要关键部分 |
